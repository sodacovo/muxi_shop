# 🛒 muxi_shop — 高并发秒杀商城

> **一个面向中小型电商、轻量级但生产可用的全栈商城系统。**
> 用户端 + 管理后台 + 秒杀引擎，Django + Vue + Redis + RabbitMQ + Celery 全家桶。
> 重点不在"调通 API"，而在**真把秒杀这件事在工程上做对**。

## 🎯 核心业务：秒杀引擎

秒杀是整个系统最复杂的模块，也是这套 README 最值得讲清楚的部分。

### 业务规则

- **场次制**：管理员后台配置秒杀活动（开始时间、结束时间、商品、**秒杀价**、**秒杀库存**、**单人限购**）
- **用户路径**：商品详情 → 秒杀按钮 → 排队/抢购结果页 → 下单 → 支付 → 订单详情
- **限购**：同一用户同一活动最多买 N 件（按 `user_id + activity_id` 维度去重）
- **库存独立**：秒杀库存和日常库存是**两套**（秒杀库存用 Redis 控制，日常库存走 MySQL），活动结束释放

### 关键工程问题怎么解

| 问题 | 解法 | 为什么不那么做 |
|------|------|----------------|
| **超卖** | Redis Lua 把"判断库存 + 扣减"包成原子操作 | 不能用 `GET → DECR`，两步中间会被插入；也不能 `DECR → 判断 < 0 → INCR 回滚`，库存会出现负数再恢复 |
| **重复下单** | `user_id + activity_id + sku_id` 三元组做幂等键（Redis SETNX） | 用户狂点、客户端重试、网络重发都会产生重复请求 |
| **数据库被打垮** | Redis 挡掉 99% 失败请求，只有成功请求才走异步 | 不能让每个请求都打 MySQL |
| **HTTP 阻塞** | 同步链路只做"参数校验 + 入队"，订单创建交给 Celery | 不能让用户等十几秒看转圈 |
| **Worker 任务丢失** | `ACKS_LATE` + `REJECT_ON_WORKER_LOST` + 死信队列 + 补偿事件 | 不能让 Worker 挂一下就少一单 |
| **同一 SKU 并发处理冲突** | Redis 分布式锁 `SET NX EX 10` + 后台续约线程 | 不能让两个 Worker 同时给一个 SKU 落库 |
| **误删别人的锁** | 释放锁时用 Lua 校验 `task_id` 匹配再 DEL | 不能直接 `DEL`，锁过期被别人拿到就被误删 |
| **Redis 扣了但 MySQL 没创建** | Saga 模式：失败时 `INCRBY` 回滚 Redis 库存 | Redis / MySQL 没法强一致，必须有补偿 |
| **支付超时未付** | 订单创建后启动 15 分钟支付倒计时，超时自动取消并回滚库存 | 不能让库存被白占着 |

## 🧱 技术选型说明

| 类别 | 选型 | 为什么选它 |
|------|------|----------|
| 后端框架 | Django 4.x + DRF | 生态成熟，Admin 后台免费送，序列化器省一堆样板代码 |
| 异步任务 | Celery + RabbitMQ | 行业标准；RabbitMQ 比 Redis Stream 多了确认机制和死信队列 |
| 缓存 & 锁 | Redis（Lua 脚本） | Lua 把多步操作包成原子，是秒杀场景的标准解法 |
| 数据库 | MySQL 8 | 事务、行锁、MVCC 都齐全，订单系统首选 |
| 前端 | Vue 3 + Vite + Pinia | 用户端和管理后台两套独立工程，组件复用 |
| 反向代理 | Nginx | HTTPS 终结 + 静态资源 + 多子域名分发 |
| 部署 | Docker Compose | 一键起 Redis / RabbitMQ / MySQL，本地 / 演示环境够用 |

**为什么不用 Spring Cloud / 微服务**：
秒杀是**有界上下文**，商城主业务体量没到需要拆微服务的程度。单体 Django + 多 Worker 水平扩展已经能扛住中小型电商的秒杀流量。**过度设计比设计不足代价更高**。

## ✨ 这个项目里值得展开讲的几个设计点

### 1. 秒杀库存和日常库存分离

日常商品有库存，秒杀活动有独立库存（`seckill_stock`）。秒杀扣的是 Redis 里的 `seckill_stock`，落库后才同步减 MySQL 里的 `daily_stock`。
- **好处**：秒杀结束不会污染日常销售，活动结束后库存合并
- **代价**：要维护两套库存一致性 → 用 Saga 补偿兜底

### 2. 限购 vs 防重复下单

两者不一样：
- **限购**（业务规则）：一个用户最多买 2 件 → 用 Redis 计数器 `user_limit:{user_id}:{activity_id}`
- **防重复下单**（幂等）：同一请求被发 3 次 → 用 `order_idempotent:{user_id}:{sku_id}` SETNX

代码上分两个 Redis key，监控报警也是分两条线。

### 3. 分布式锁的 TTL 续约

锁的 TTL 是 10 秒，业务可能跑 15 秒。解决思路：
- 后台线程每 3 秒检查一次，锁还是自己的就续到 10 秒
- 给 Worker 设置**最大执行时间**（30 秒），超时主动停止续约并退出
- 释放锁用 Lua 校验 `task_id`，避免误删别人的锁

生产环境推荐用 **Redisson WatchDog**，自己写线程只作为学习和兜底方案。

### 4. 订单状态机

订单有严格的状态流转：

```
待付款 ──支付回调成功──► 待发货 ──商家发货──► 待收货 ──用户确认──► 已完成
   │                       │                     │
   │15分钟超时              │商家取消              │用户退货
   ▼                       ▼                     ▼
 已取消                   已取消                退款中
```

所有状态流转都走 `Order.state_transition()` 方法，**禁止跨状态直接改字段**，避免出现"已取消的订单又被发货"这种 bug。

### 5. 防刷与风控

- **IP 限流**：同一 IP 每秒最多 10 次秒杀请求（Redis 滑动窗口）
- **用户限流**：同一用户每秒最多 1 次（前端按钮也加 1 秒防抖）
- **设备指纹**：用户级限购考虑 `user_id + device_id`
- **黑名单**：被风控标记的 IP / user_id 直接拒绝

## 🚀 一键启动

```bash
# 1. 起中间件
docker-compose up -d redis rabbitmq mysql

# 2. 初始化数据库
python manage.py migrate
python manage.py createsuperuser

# 3. 同步商品库存到 Redis（管理后台也有入口）
python manage.py sync_seckill_stock

# 4. 起 Worker（至少 2 个实例才能看到分布式锁效果）
celery -A muxi_shop worker -l info -c 4
celery -A muxi_shop beat -l info     # 处理超时订单、续约线程

# 5. 起 Web 服务
python manage.py runserver 0.0.0.0:8000

# 6. 起前端
cd muxi_shop_web && npm run dev      # 用户端
cd admin.nwq1309.shop && npm run dev # 管理后台
```

环境变量示例见 `.env.example`，所有密钥均已脱敏。

## 🧠 我从做这个项目学到的

1. **秒杀是工程问题，不是算法问题**。真正的难度在于「不超卖 + 不丢任务 + 不阻塞 + 不误删锁」，每一项都是一行行代码 + 一次次压测调出来的。
2. **不要重复造轮子，但要理解轮子**。自己实现分布式锁续约是为了懂原理，生产环境用 Redisson 更稳。
3. **Lua 解决"瞬间"，分布式锁解决"业务临界区"**。两层是协作关系，不是替代关系。
4. **幂等是异步系统的入场券**。没有幂等，RabbitMQ 重投就是双扣双发。
5. **Redis 和 MySQL 永远不可能强一致**。Saga 补偿不是 hack，是工程化的最终一致方案。
6. **过度设计的代价 > 设计不足**。单体 Django + 多 Worker 已经能扛中小电商的秒杀流量，不要为"未来"拆微服务。
